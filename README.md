# doubak-import-adapters

[![test](https://github.com/Doubak/doubak-import-adapters/actions/workflows/test.yml/badge.svg?branch=main)](https://github.com/Doubak/doubak-import-adapters/actions/workflows/test.yml?query=branch%3Amain)

> **这是源码仓库。** 项目主页在 **<https://doubak.com>**。

将**第三方抓取工具**此前保存的豆瓣页面，转换为豆备（Doubak）标准的 **bundle** 归档格式。转换完成后，
可直接交由 [doubak-data-parser](https://github.com/Doubak/doubak-data-parser) 无缝解析 ——
进而生成标准 canonical 数据、构建独立归档站点或导出至 NeoDB 等平台。

```sh
node bin/import.js <第三方工具的产出目录> <输出目录> [--timezone=Asia/Shanghai]
npm test    # node --test，零依赖，不需要 npm install
```

需要 Node ≥ 20。

## 支持的来源

| 工具 | 状态 | 实测规模 |
|---|---|---|
| [its-my-data/doubak](https://github.com/its-my-data/doubak)（前代的 Go 抓取工具） | ✅ | 782 MB / 7353 个页面 / 2022-12-25 → 2024-08-11 |

**表中每一项均基于真实历史归档实测验证。** 编写一个表面看似可行的转换器并不难，但任何细微的转换偏差，往往要等到下游 canonical 解析阶段才会暴露出来。因此，未经真实数据检验的适配逻辑不会纳入支持列表。

## 这不是「解析老 HTML」

原始 HTML 页面内容无需改动，完整保留原始字节。适配的核心任务是**补全第三方工具未记录的元数据**：

| bundle 字段 | 来源渠道 | 可靠性说明 |
|---|---|---|
| `intent` / `route_key` | 文件名 | 确定可靠 |
| `url` | 文件名 + 媒介的域名规则 | **算法重建**（详见后文） |
| `observed_at` | 文件名的时间戳，精确到分钟 | **重建推导**，时区默认假定 |
| `verdict` | 跑一遍抓取器分类器 | 基于页面真实正文重跑分类判定 |
| `coverage.claimed_count` | 页面 `<h1>` 里的 `(1157)` | 确定可靠 |
| `crawl_state.contiguous` | 文件名里的分页区间 | 确定可靠 |
| `account.user_id` | 页面里的 `USER_ID` × 广播页的 `data-uid`，两者互相印证 | 相互核对验证（冲突时终止处理） |
| HTTP 响应头 / 状态码 | **无原始记录** | 详见后文 |

### 补充生成的元数据必须显式标注

每一行 index 都写着 `capture_fidelity: "decoded_body+synthesized_headers"`
（bundle/1.3 为此新增的取值）。它的含义精确地是：

> **页面正文完全真实，HTTP 响应头为本地合成伪造。**

规范 [§6.4.1](https://spec.doubak.com/bundle/v1/) 明确禁止将其标注为
`decoded_body+filtered_headers` —— 后者代表响应头确实来自真实服务器返回、仅经过浏览器过滤。
在数据溯源与归档取证中，必须严格区分「被过滤的真实头部」与「本地推导合成的伪造头部」。

在此原则下：

- **不主动写入 `http_status`。** WARC 的 response 记录在协议结构上强制要求状态行；
  但 index 索引中的状态字段为可选，尽可能避免伪造数据。
- 所有重建与推导规则均写入 `manifest.notes` 以及归档的 `README.txt`（中英双语），
  完整保留数据生成的上下文与推导逻辑。

### 页面判定（verdict）严格依正文重新校验

响应头可以基于规则合成，但页面分类与有效性判定绝不能主观臆测。判定必须直接基于真实的正文内容进行分析。

这在实践中尤为关键。前代工具曾将未登录状态下的登录页直接按正常数据文件名保存，未附加任何状态标记 ——
下游解析器仅能感知到「文件存在，内容为 0 条记录」。实测在 7353 个历史页面中：

```
ok        5051        login  2270        soft404  25        unknown(0 字节)  7
```

在上述 2270 个未登录页面中，包含了 2023-01-27 当天的整批抓取（141 个列表页及所有作品详情页）。
未登录时渲染的列表页表面结构正常，但关键的标记标签栏并未输出。若不做严格校验照单全收：

```
未校验导入   3049 条修订 / 2534 条记录     ← 其中 2856 条修订属于失效页面引发的误判
严格校验导入  193 条修订 / 2526 条记录
```

严格过滤仅损失了 1 条别处未收录的有效标记，却避免了数千条脏数据的混入。

那 7 个 0 字节文件与 25 个 soft404 同理：`items/20230127.1406_movie_4099277.html`
是一张豆瓣的「页面不存在」，17 KB，被当成作品详情页存了下来。

## 实测：接进真实档案之后

把 2022-12 → 2024-08 那 7 份导入档案，和扩展 2026 年抓的 17 份放进同一个目录一起解析：

| | 只有 2026 那 17 份 | 加上导入的 7 份 | 变化 |
|---|---|---|---|
| 标记 | 2950 | **2955** | +5 |
| 广播 | 3411 | **3413** | +2 |
| 标记修订 | 2959 | **3105** | **+146** |
| 广播修订 | 3480 | **3856** | **+376** |
| 多修订的标记 | 8 | **147** | **×18** |

**总条目记录数仅增加 7 条，但其核心价值在于历史脉络的补全。** 原有 canonical 的编辑史仅包含 9 次修订（因首次完整抓取时间为 2026-07）。接入这批历史导入归档后，补齐了过去 20 个月里真实发生过的所有修改演变 —— 这些演变在豆瓣现网早已无法追溯：

```
movie/26869078   （identity_layer: degraded_key，upstream_id 3199573829）
  2022-12-26 → 2023-12-18   wish   “又来了，先听歌再马克剧”
  2024-08-11                doing  “开始看了，想起来是 Aimyon 的主题曲……//又来了，先听歌再马克剧”
  2026-07-31 → 2026-08-01   done   ★3  “感觉是东京郊区宣传片……//开始看了……”
```

一条完整的 想看 → 在看 → 看过，跨四年，豆瓣页面上只剩最后那一行。

### 成功挽救已被豆瓣删除的条目原名

此前曾初步推测「无法找回已被豆瓣删除的作品原名」，该推论源于初期对单一案例 `game/26794548`（《返校》）的观察（其在 2022-12-25 广播卡片上即已显示为「未知条目」）。但在合并历史数据重新全量统计后，发现 8 个已下架条目中有 3 个在历史归档中完整保留了原名：

```
movie/11611021   在这世界的角落 / この世界の片隅に
game/24299254    瘟疫公司 Plague Inc.
game/27054820    瘟疫公司：物竞天择 Plague Inc: Evolved
```

历史归档记录下了平台下架删除前的真实页面状态。《返校》未找回是因为其在更早时期就已被下架。

解析器对此类墓碑数据的测试断言相应设置为**下界约束**（「至少 3 个」）而非绝对相等：后续若导入更早期的历史数据，有望恢复更多被删除作品的原名，避免因找回更多条目而导致测试失败。

## 当前已知局限

- **不包含图片资源。** 第三方抓取工具仅保存了 HTML。摄取广播时 canonical 会引用 20 个缺失字节的图片 URL。这不是缺陷，而是该数据源未抓取图片路线 —— 解析器的断言专门验证这 20 个缺失项，以确保分类依据与数据完整性边界清晰。
- **缺失日记 / 影评 / 豆列 / 相册** —— 原工具未覆盖这些数据路线。
- **早期未登录状态下抓取的数据全量丢弃**（包含 149 个列表页、2 个广播页及当天详情页）。

## 如何新增适配来源

编写新适配器时需明确以下核心问题（按重要性排序）：

1. **如何确定 `intent`（抓取意图）？** 规范将 intent 列为「一旦丢失则事后无法完全推导」的核心元数据：例如一份标记列表的第 7 页，仅看页面结构无法可靠推断其属于「看过」还是「想看」。its-my-data/doubak 在文件名中携带了状态参数，使得推导成为可能。若外部数据源无法明确 intent，其解析价值与完备性将受到很大限制，且必须在归档文档中如实注明。
2. **账号归属判定：** 一个 bundle 只能归属于单一账号。若账号判定错误，会导致该数据在下游合并阶段与他人档案混淆，且合并后的 canonical 无法自动分离。
3. **如何划分单次抓取批次？** 核心判定规则只有一条：**同一采集路线下的关联页面不得拆分到两份独立的 bundle 中**，否则两份归档均无法满足连续性证明，会导致一次完整的全量抓取被误判为两次不完整的残缺抓取。

在代码结构上：实现 `src/adapters/<工具名>.js`（纯函数，仅负责「文件名/目录结构 → 单次捕获元数据」的映射），底层的 `src/convert.js` 与 `src/scan.js` 均为通用复用模块。

## 为何直接复用扩展代码，而非独立实现

`src/vendor/` 为 `doubak-extension` 中对应 9 个核心模块的源码复用副本，由 `node tools/sync-vendor.mjs --check` 严格保障代码同步状态（在本地测试与 CI 中均会校验）。

如需修改，统一在 extension 仓库调整后重新同步。这是为了确保本工具输出的 bundle 归档与浏览器扩展在底层实现与行为逻辑上完全保持一致。许多工程约束（如段轮转边界保护、文件偏移量计算基准、`advanced=true` 的连续性保障、`floor_time` 与 `enumeration` 的互斥约束等）直接由写入器核心代码约束，而不仅停留在 JSON Schema 层面。

页面分类器（`classifyResponse`）同样如此。其中的每一项判定规则均基于大量真实历史页面的实测与逆向分析得出，包括处理历史归档中的 0 字节空页面、异常跳转页与不同时期的广播页面格式。直接复用成熟的分类逻辑，避免了重复踩坑与判定规则漂移。

仅有底层存储抽象 `src/file-store.js` 未复用：浏览器扩展面向 OPFS（源私有文件系统）写入，而本工具面向本地文件系统操作，属于正常的运行环境差异。

## 验证与检查

```sh
# 规范仓库自带的参考校验器（npm test 中也会执行）
#   退出码 0: 校验通过 / 1: 合规性错误 / 2: 完整性损坏
python3 ../doubak-data-specs/bundle/v1/validate.py <输出目录>/doubak-bundle-*

# 基础完整性与哈希核验（零第三方依赖）
node ../doubak-data-parser/bin/verify.js <输出目录>

# 解析为 canonical 数据（默认自动运行字节校验）
node ../doubak-data-parser/bin/parse.js <输出目录> <canonical 输出目录>
```

**由外部数据导入生成的归档更应进行严格校验。** 浏览器扩展抓取的 bundle 在生成时按流式直接写入，而导入适配器需要重新组装与索引数据：文件偏移量、记录 ID 以及 `content_sha256` 哈希等均由适配逻辑重新计算并写入。严格的全量校验是检验重组逻辑与数据一致性最可靠的手段。
