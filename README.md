# doubak-import-adapters

[![test](https://github.com/Doubak/doubak-import-adapters/actions/workflows/test.yml/badge.svg?branch=main)](https://github.com/Doubak/doubak-import-adapters/actions/workflows/test.yml?query=branch%3Amain)

> **这是源码仓库。** 项目主页在 **<https://doubak.com>**。

把**别的抓取工具**存下来的豆瓣页面，转成豆备 (Doubak) 的 **bundle** 档案格式。转完之后，
[doubak-data-parser](https://github.com/Doubak/doubak-data-parser) 一行都不用改就能读它们——
于是那些页面能进 canonical、能生成站点、能导出到 NeoDB。

```sh
node bin/import.js <第三方工具的产出目录> <输出目录> [--timezone=Asia/Shanghai]
npm test    # node --test，零依赖，不需要 npm install
```

需要 Node ≥ 20。

## 支持的来源

| 工具 | 状态 | 实测 |
|---|---|---|
| [its-my-data/doubak](https://github.com/its-my-data/doubak)（前代的 Go 抓取工具） | ✅ | 782 MB / 7353 个页面 / 2022-12-25 → 2024-08-11 |

**每一行都是跑过真实档案的。** 一个只写了代码没跑过真数据的适配器不该出现在这张表里——
写一个「看起来对」的转换器很容易，而它错在哪儿要等到解析出来的 canonical 里才看得见。

## 这不是「解析老 HTML」

页面本身不用动，它们是真的字节。要补的是**那批工具没有记录的元数据**：

| bundle 字段 | 从哪儿来 | 靠不靠谱 |
|---|---|---|
| `intent` / `route_key` | 文件名 | 确定 |
| `url` | 文件名 + 媒介的域名规则 | **重建**（见下） |
| `observed_at` | 文件名的时间戳，精确到分钟 | **重建**，且时区是假定的 |
| `verdict` | 跑一遍抓取器那份分类器 | 读的是正文，正文是真的 |
| `coverage.claimed_count` | 页面 `<h1>` 里的 `(1157)` | 确定 |
| `crawl_state.contiguous` | 文件名里的分页区间 | 确定 |
| `account.user_id` | 页面里的 `USER_ID` × 广播页的 `data-uid`，两者互相印证 | 对不上就停下来 |
| HTTP 响应头 / 状态码 | **没有** | 见下 |

### 补出来的东西必须标明是补的

每一行 index 都写着 `capture_fidelity: "decoded_body+synthesized_headers"`
（bundle/1.3 为此新增的取值）。它的含义精确地是：

> **正文是真的，响应头是编的。**

规范 [§6.4.1](https://spec.doubak.com/bundle/v1/) 明令不许把它降级成
`decoded_body+filtered_headers`——那个取值宣称响应头来自服务器，只是被浏览器过滤过。
**「被过滤的真头部」与「凭空造的假头部」之间的区别，恰恰是取证时唯一要问的那个问题。**

同一条原则往下推：

- **`http_status` 不写。** WARC 的 response 记录结构上必须有个状态行，那没办法；
  但 index 里那个字段是可选的，**能不编就不编**。
- 重建规则写进 `manifest.notes` 与档案的 `README.txt`（中英双语），让读者自己判断
  这些值是怎么来的。

### verdict 照判不误

头部可以编，判定不可以。判定读的是正文，而正文是真的。

这不是个理论问题。前代工具**把登录页按数据文件名写在了磁盘上，没有任何标记**——
下游只会看到「文件在，里面 0 条」。实测那 7353 个页面里：

```
ok        5051        login  2270        soft404  25        unknown(0 字节)  7
```

那 2270 个 login 里有整整一次抓取（2023-01-27，141 个列表页 + 那一天全部的作品详情页）。
未登录渲染出来的列表页**看起来完全正常**，只是标签那一栏根本不渲染。照单全收的话：

```
天真摄取   3049 条修订 / 2534 条记录     ← 2856 条是凭空捏造的
诚实摄取    193 条修订 / 2526 条记录
```

而**代价只有 1 条**别处没有的标记。这个不对称大到没什么可讨论的。

那 7 个 0 字节文件与 25 个 soft404 同理：`items/20230127.1406_movie_4099277.html`
是一张豆瓣的「页面不存在」，17 KB，被当成作品详情页存了下来。

## 实测：接进真实档案之后

把 2022-12 → 2024-08 那 7 份导入档案，和扩展 2026 年抓的 17 份放进同一个目录一起解析：

| | 只有 2026 那 17 份 | 加上导入的 7 份 | 变化 |
|---|---|---|---|
| 标记 | 2950 | **2955** | +5 |
| 广播 | 3411 | **3413** | +2 |
| 标记修订 | 2959 | **3105** | **+146** |
| 广播修订 | 3480 | **3856** | **+376** |
| 多修订的标记 | 8 | **147** | **×18** |

**记录数只多了 7 条。价值不在这里。** 现在的 canonical 整部编辑史只有 9 条修订，因为
第一次抓取是 2026-07。导入之后多出来的是**那 20 个月里真实发生过的编辑**——豆瓣自己
不保存的东西：

```
movie/26869078   （identity_layer: degraded_key，upstream_id 3199573829）
  2022-12-26 → 2023-12-18   wish   “又来了，先听歌再马克剧”
  2024-08-11                doing  “开始看了，想起来是 Aimyon 的主题曲……//又来了，先听歌再马克剧”
  2026-07-31 → 2026-08-01   done   ★3  “感觉是东京郊区宣传片……//开始看了……”
```

一条完整的 想看 → 在看 → 看过，跨四年，豆瓣页面上只剩最后那一行。

## 已知做不到的

- **救不回被豆瓣删掉的作品名。** 实测 0/8。`game/26794548`（《返校》）在 **2022-12-25
  的广播卡片上就已经是「未知条目」**了——豆瓣删掉它是在这批档案开始之前。
- **一张图片都没有。** 老工具只存 HTML。摄取广播会让 canonical 引用 22 个没有字节的
  图片 URL（这是已知缺口，不是新问题：解析器那边有一条断言要求 canonical 引用的图
  等于档案里的 `asset.status_photo`）。
- **没有日记 / 影评 / 豆列 / 相册**——老工具没有这些路线。
- **未登录抓的那一代整个丢掉**（149 个列表页 + 2 个广播页 + 那一天的详情页）。

## 怎么再加一个来源

一个适配器要回答的问题，按重要性排：

1. **`intent` 从哪儿来？** 规范把它列为三个「丢了就永远补不回来」的字段之一：
   一份标记列表的第 7 页，事后无法区分它当初是「看过」还是「想看」的第 7 页。
   its-my-data/doubak 恰好把状态写进了文件名——**那是运气，不是设计**。答不出来的话，
   那批数据的价值会低很多，而且这一点必须说出来，不能糊过去。
2. **账号是谁？** 一个 bundle 只能属于一个账号，而安错账号的后果是它会跟别人的档案
   在同一个目录里被合并，合并过的 canonical 事后拆不开。
3. **一次抓取怎么切？** 判据只有一条：**一条路线的页面不能被劈进两份档案**，否则它的
   连续性证明在两边都不成立，一次完整的枚举会被记成两次不完整的。

代码上：新写一个 `src/adapters/<工具名>.js`（纯函数，只做「文件名/目录结构 → 这次捕获
是什么」），`src/convert.js` 与 `src/scan.js` 是共用的。

## 为什么是抄一份，不是自己写一份

`src/vendor/` 是 `doubak-extension` 里那 9 个文件的**逐字节拷贝**，由
`node tools/sync-vendor.mjs --check` 守着新鲜度（测试与 CI 都会跑）。

要改就去那个仓库改，然后回来同步。理由是这个仓库产出的东西和扩展产出的东西**必须是
同一种格式**——不是「都符合规范」，是同一份实现。规范里有一批约束根本不在 JSON Schema
里，而在写入器的代码里：段轮转不许劈开一条记录、偏移量取自写入前的文件长度、
`advanced=true` 必须连续无缺口、`floor_time` 非 null 就不许写 `enumeration=full`。

分类器更是如此。`classifyResponse()` 的每一个判据都是量出来的，而且**相当一部分就是
对着这个仓库要导入的那批老页面量的**——它的注释里写着「旧档案里 6341 个作品详情页中有
7 个是 0 字节」「2022-12 → 2024-08 共 403 个广播页」。在这边重写一份判定逻辑，等于把
那些实测结论重新猜一遍。

不搬的是 `src/file-store.js`：**「字节往哪儿去」是宿主差异**，扩展写 OPFS，这边写文件
系统。这条线与解析器那边的 `bundle-source.js` 是同一条。

## 验一遍

```sh
# 规范仓库自带的参考校验器（外部裁判，npm test 里也会跑）
#   退出码 0 干净 / 1 只有合规性错误（字节没问题）/ 2 有完整性错误
python3 ../doubak-data-specs/bundle/v1/validate.py <输出目录>/doubak-bundle-*

# 只核字节（零依赖，不用 Python）
node ../doubak-data-parser/bin/verify.js <输出目录>

# 解析成 canonical —— 字节校验默认就跑
node ../doubak-data-parser/bin/parse.js <输出目录> <canonical 输出目录>
```

**导入产出的档案尤其该核一遍。** 抓取产出的 bundle 是浏览器一条条写下来的，
而导入产出的是这个工具**重新组装**的：偏移量、记录 id、`content_sha256` 全是这边
算出来再写进索引的，算错了写出来的档案照样打得开、照样能解析。核一遍是
「组装对不对」唯一的外部证据。
